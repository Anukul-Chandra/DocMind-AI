# DocMind AI — Architecture Report

## 1. Overview

DocMind AI is a **Retrieval-Augmented Generation (RAG) document analysis system**. Users upload PDFs, which are chunked, embedded, and stored in a FAISS vector index; they then ask natural-language questions and receive grounded answers generated by an LLM provider using only the retrieved context.

The system is a **Python backend only** (no frontend yet), built with **FastAPI**, and designed around layered, dependency-injected services with a strong commitment to Clean Architecture and SOLID principles. It is backend-only, FastAPI-driven, with local JSON persistence by default and a PostgreSQL backend prepared via SQLAlchemy + Alembic.

```
User ──▶ FastAPI API ──▶ Services (orchestration) ──▶ Retrieval / LLM / Storage
                          │
                          └──▶ Repositories (JSON | Postgres)
```

## 2. Tech Stack

| Concern | Technology |
|---|---|
| Web framework | FastAPI 0.139 + Uvicorn |
| Validation | Pydantic v2 + pydantic-settings |
| Embeddings | `sentence-transformers` (`all-MiniLM-L6-v2`, 384-dim) |
| Vector search | FAISS (`faiss-cpu`, `IndexFlatL2`) |
| PDF parsing | PyMuPDF |
| Chunking | `langchain-text-splitters` (recursive character splitter) |
| LLM gateways | OpenRouter (OpenAI SDK), Google Gemini (`google-genai`), Groq, httpx streaming |
| Persistence (default) | Local JSON files |
| Persistence (alt) | PostgreSQL 17 via SQLAlchemy 2 + psycopg3 |
| Migrations | Alembic |
| Infra | Docker Compose (PostgreSQL only) |

## 4. Layered Architecture

The codebase follows a clean, dependency-inverted onion:

| Layer | Modules | Responsibilities |
|---|---|---|
| **Interface / Web** | `app/api/*`, `app/main.py` | HTTP routing, request validation, error envelopes, DI via Depends |
| **Application / Orchestration** | `app/services/chat`, `app/services/document`, `app/services/indexing` | Sequence use-cases: index → retrieve → prompt → generate |
| **Domain / Providers** | `app/services/retrieval`, `app/services/llm/*`, `app/services/embedding`, `app/services/vectorstore` | Retrieval algorithms, LLM providers, embedding, stores |
| **Persistence** | `app/repositories/*`, `app/db/*`, `app/services/storage` | Repositories behind ABC interfaces; JSON or Postgres backends |

**Dependency rule:** high-level services depend on abstractions (`Retriever`, `DocumentRepository`, `BaseProvider`) injected via constructors (`app/api/dependencies.py`), never on concrete internals. Providers themselves know nothing about settings globals — config is injected.

## 5. Core Subsystems

### 5.1 Configuration (`app/core/config.py`)

- A single `Settings` pydantic-settings class loads from env / `.env`.
- Paths are anchored to `backend/` at runtime via a `model_validator`, making persistence machine-independent.
- Key knobs: chunk size/overlap (1000/200), embedding model, provider priority (`openrouter,gemini,groq`), API keys, `persistence_backend` (`json`|`postgres`), storage paths.

### 5.2 Web / API Layer

**App assembly (`main.py`):** creates the `FastAPI` app, registers global exception handlers, includes four routers (root/health, retrieve, chat, documents).

**Routing:**

| Method | Path | Purpose |
|---|---|---|
| GET | `/`, `/health` | Status/health |
| POST | `/retrieve` | Raw chunk retrieval (uses `HybridRetriever`) |
| POST | `/chat/` | RAG question-answer (NEW `ChatService`) |
| POST | `/chat/stream` *(removed in latest rewrite)* | SSE streaming (old service) |
| POST | `/documents/upload` | Upload + index PDF |
| GET | `/documents`, `/documents/{id}` | List / get documents |
| DELETE | `/documents/{id}` | Soft-delete document |

**Dependency injection (`dependencies.py`):** `@lru_cache`-cached factories for the embedding service, FAISS `VectorStore` (loaded from disk), `MetadataStore` (loaded from JSON), the `HybridRetriever`, repositories, and two chat services — `get_chat_service` (legacy, memory + logging) and `get_rag_chat_service` (new, minimal).

**Error handling (`errors.py`):** every exception is rendered through a standard envelope `{success, error:{code, message}}` with stable machine-readable codes (`bad_request`, `not_found`, `validation_error`, `bad_gateway`, …).

**Transport models (`models/responses.py`):** generic `SuccessResponse[T]` envelope, `ErrorResponse`, plus typed payloads (`UploadResult`, `DeleteResult`, `MessageData`, `HealthData`).

### 5.3 Chat / RAG subsystem

Two generations coexist:

- **Legacy (`services/chat/service.py`)** — full-featured `ChatService` with conversation memory, request logging, source attribution, and SSE streaming.
- **New (`services/chat/chat_service.py`)** — minimal orchestration layer: injects `Retriever`, `PromptBuilder`, `ProviderManager`; exposes only `async chat(question: str) -> LLMResponse`; knows nothing about concrete providers. Exposed via `POST /chat/`.

**RAG flow (new ChatService):**
```
question
  → Retriever.retrieve(question)          # top-k chunks (dicts with text/filename/chunk_id)
  → PromptBuilder.build_prompt(question, contexts)  # grounded prompt + source metadata
  → ProviderManager.generate(prompt.text) # failover across providers
  → LLMResponse(text, provider, model)
```

### 5.4 Document indexing subsystem

Two generations again:

- **Legacy (`services/indexing/document_index_service.py`)** — `DocumentIndexService` (3 deps) used by `/documents/upload`; persists FAISS index + metadata to disk; returns `DocumentIndexResult`.
- **New (`services/document/`)** — `DocumentService` (5 deps: `PDFProcessor`, `Chunker`, `EmbeddingService`, `VectorStore`, `MetadataStore`) with `async index_document(file_path)`; extract → clean → chunk → embed → add to FAISS → add metadata → `IndexDocumentResult(filename, chunks, status="indexed")`.

**Indexing flow:**
```
PDF file
  → PDFProcessor.extract_text           # PyMuPDF
  → clean_text                          # whitespace normalization
  → Chunker.chunk                       # recursive splitter (1000 chars / 200 overlap)
  → EmbeddingService.generate_embeddings  # sentence-transformers (384-d)
  → VectorStore.add_embeddings          # FAISS IndexFlatL2
  → MetadataStore.add_documents         # chunk metadata (workspace, filename, chunk_id, text)
  → (legacy) persist index + metadata to disk
```

### 5.5 Retrieval subsystem (`services/retrieval`)

- **`Retriever`** — ABC interface (`retrieve`, `is_eligible`); the sole abstraction `ChatService` depends on.
- **`SemanticRetriever`** (`vectorstore/retriever.py`) — embeds query, FAISS nearest-neighbor search, maps indices to metadata, filters by workspace + deletion.
- **`BM25Retriever`** — Okapi BM25 keyword scoring; lazily builds term statistics from the shared `MetadataStore` (no duplicated storage).
- **`HybridRetriever`** — merges semantic + BM25 via **Reciprocal Rank Fusion (RRF, k=60)**, deduplicates on `(workspace_id, filename, chunk_id)`, then reranks.
- **`Reranker`** — protocol-based; default `SemanticReranker` is dependency-free (token cosine similarity). Pluggable for Cohere/Jina/BGE later.

### 5.6 LLM provider subsystem (`services/llm`)

- **`BaseProvider`** (ABC) — `generate()` (+ default `generate_stream()` fallback). Error taxonomy `ProviderError` → `AuthenticationError`, `RateLimitError`, `APIError`, `InvalidResponseError`; all recoverable to enable failover.
- **Concrete providers** — `OpenRouterProvider` (httpx, native SSE streaming, model rotation), `GeminiProvider` (`google-genai`), `GroqProvider`. All constructor-injected config; none touch global settings.
- **`ProviderManager`** — iterates providers in priority order, fails over on `ProviderError`, aggregates errors, raises `LLMUnavailableError` when all fail. Streaming variant keeps a provider once streaming begins.
- **`ModelPoolManager`** — round-robin pool of OpenRouter models.
- **`ModelCatalogService`** — discovers free OpenRouter models (`:free`) at startup, falls back to a static default list on failure.
- **`PromptBuilder`** — builds the grounded prompt (system + context + history + question) and returns `RAGPrompt(text, sources)`.
- **`factory.py`** — composition root that builds the `ProviderManager` from `settings.provider_priority`.

### 5.7 Vector store & metadata (`services/vectorstore`, `services/vector_store.py`)

- **`VectorStore`** — wraps `faiss.IndexFlatL2`; `add_embeddings`, `search`, save/load index.
- **`MetadataStore`** — in-memory list of chunk dicts; `add_documents`, `get_document`, JSON save/load. Shared by semantic + BM25 retrieval.
- **`workspace.py`** — `DEFAULT_WORKSPACE`, `Workspace` value object, in-memory `WorkspaceStore`.

### 5.8 Persistence layer (`repositories`)

- **ABC interfaces** (`interfaces.py`): `DocumentRepository`, `WorkspaceRepository`, `ConversationRepository`, `LogRepository` — services depend on these, not implementations (DIP).
- **JSON implementations** (`repositories/json/`): back `DocumentRegistry` (soft-delete via `documents.json`), JSON conversation/log/workspace stores.
- **PostgreSQL implementations** (`repositories/postgres/`): SQLAlchemy repos (`documents`, `workspaces`, `conversations`, `chat_messages`, `request_logs`, placeholder `users`) behind the same interfaces, driven by `persistence_backend` + `database_url`. A `User` model exists as a placeholder, not yet wired.
- **Storage util** (`services/storage/json_file_store.py`) — shared JSON read/write with parent-dir creation.

### 5.9 Observability

- **`RequestLogger`** — appends structured `RequestLogEntry` records to daily `YYYY-MM-DD.jsonl` files; best-effort (never raises). Logged by the legacy chat service and usable from the new one.

## 6. Key Architectural Properties

| Principle | Implementation |
|---|---|
| **Single Responsibility** | Each service orchestrates one use-case; providers only generate; retrievers only retrieve |
| **Open/Closed** | `ProviderManager` accepts any `BaseProvider`; `Reranker` protocol is pluggable; repositories swap JSON↔Postgres |
| **Liskov** | All providers/retrievers conform to their ABC contracts (e.g., default `generate_stream` fallback) |
| **Interface Segregation** | Small focused ABCs per concern (`Retriever`, `DocumentRepository`, `BaseProvider`) |
| **Dependency Inversion** | High-level services get collaborators injected; never import concrete providers/stores |
| **Clean Architecture** | Web → application → domain → persistence; transport models isolated in `app/models`; providers unaware of FastAPI |

## 7. Notable Observations & Risks

1. **Dual implementations in transition.** Two `ChatService`s and two document-indexing services exist (legacy `service.py`/`document_index_service.py` vs new `chat_service.py`/`document_service.py`). The new `POST /chat/` uses the new stack; `/documents/upload` still uses the legacy indexing service. The legacy streaming/memory endpoints were removed in the last route rewrite.
2. **Secrets hygiene.** `.env` files and `.lh/` history were previously committed to git (flagged in commit history); API keys are currently injected from settings but the repo history should be scrubbed and `.gitignore` updated.
3. **In-memory hot path.** `VectorStore` and `MetadataStore` are cached singletons loaded at startup; FAISS vectors are only persisted by the legacy indexing service — the new `DocumentService` does not yet save to disk.
4. **`requirements.txt` is UTF-16** encoded at repo root (unusual; pip works but tooling may mis-parse).
5. **Deletion is soft-only** — FAISS vectors remain after a document is deleted; only metadata filters them out.
6. **PostgreSQL backend is prepared but not default** (`persistence_backend="json"`), and the `User` model is unused.

## 8. Runtime Data (`backend/storage/`)

- `faiss/index.faiss` — persisted vector index
- `metadata.json` — chunk metadata
- `documents.json` — document registry (soft-deletes)
- `logs/*.jsonl` — request logs
- Uploaded PDFs are saved into `storage/` during `/documents/upload`.

## 9. Conclusion

DocMind AI is a well-structured, dependency-injected RAG backend that cleanly separates web, orchestration, domain providers, and persistence. The architecture explicitly favors extensibility (provider failover, pluggable rerankers, swappable repositories) and is currently mid-refactor toward a simpler, focused orchestration layer (`ChatService`/`DocumentService`). The main immediate work items are consolidating the dual implementations, persisting data from the new `DocumentService`, and cleaning up secrets from git history.
